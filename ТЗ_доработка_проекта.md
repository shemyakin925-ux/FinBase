Версия 1.0 от 04.11.2026. Основание: `Описание_проекта.md` (состояние на 02.11.2026).

> **Ограничение анализа.** В репозитории сейчас лежит только `Описание_проекта.md`. Код (`pipeline/`), документы (`docs/`, `ПЛАН_дообучения.md`, `РУКОВОДСТВО_рынок_по_шагам.md`) и результаты (`EVAL/`) в git не попали. Поэтому ТЗ опирается на описание. ## 1. Цель доработки

1. Довести пилот HK до рабочего контура: данные → база → сигналы → каталог связей → агент → экран идей. Цикл обновления должен проходить без ручных правок.
2. Закрыть методические пробелы, из-за которых найденные закономерности могут оказаться завышенными: утечки, порча отложенной выборки, смещения в метках, слабая оценка качества.
3. Сделать проект воспроизводимым и защищённым от потери данных, чтобы его можно было перенести на остальные рынки.

## 3. Требования

### 3.1 Инфраструктура и воспроизводимость (П1, П2, П16)

**ИНФ-1. Репозиторий.** В git переносятся: `pipeline/`, `agent/`, `docs/`, планы и руководства, конфигурации, `resume_all.sh`, тесты. Данные, базы, модели и ключи в git не попадают (`.gitignore`).
- Ключи API хранятся только в переменных окружения или `.env`, который исключён из git. Перед первым коммитом запустить поиск секретов по истории.
- Зависимости фиксируются в `requirements.lock` или `uv.lock`.

**ИНФ-2. Манифест данных.** Для каждого слоя (`TEXT`, `SECTIONS`, `FACTS`, `PRICES`, …) хранится `MANIFEST.parquet`: путь, размер, SHA-256, дата загрузки, источник, версия скрипта. Снимки в `_snapshots/` ссылаются на манифест. Сборка базы пишет в журнал хеш манифеста, на котором она собрана.

**ИНФ-3. Резервное копирование (3-2-1).**
- Вторая копия сырых данных на отдельном диске с журналируемой ФС (APFS). Сжатие zstd уменьшит объём.
- Рабочие базы `~/llm_db/` не копируются, их пересобирает скрипт. Копируются манифесты, метки, ручные разметки, журналы гипотез и решений, золотые наборы. Это невосстановимые данные, для них нужна облачная или третья копия.
- Еженедельная проверка: выборочная сверка хешей 1% файлов.

**ИНФ-4. Очередь тяжёлых задач.** Один скрипт-диспетчер (файловая блокировка + очередь заданий):
- одновременно идёт не больше одной тяжёлой задачи (обучение, эмбеддинги, извлечение, оценка);
- процесс запускается с низким приоритетом (`nice -n 19`, `taskpolicy -b` на macOS);
- между задачами пауза 3–5 с;
- журнал задач с длительностью, пиковой памятью и кодом выхода.

**ИНФ-5. Тесты.** Минимальный набор в `pytest`, прогоняется перед каждой пересборкой базы:
- проверки целостности базы (уже есть, их нужно оформить тестами);
- тест-ловушка на утечку для каждой функции «на дату», включая агентские инструменты;
- регрессия извлечения на золотых наборах (порог не ниже текущего).

**Приёмка:** чистый клон + манифест + сырые данные → `make db && make features && make test` воспроизводит `feat_doc` с совпадением хеша (или числа строк и контрольных сумм по столбцам).

### 3.2 Методика оценки (П3, П4, П10, П11, П12)

**МЕТ-1. Единый реестр периодов** `config/splits.yaml`, его используют все модули:

| Период | Годы | Назначение |
|---|---|---|
| Разработка | ≤ 2012 | поиск гипотез, отбор признаков |
| Валидация-1 | 2013–2018 | проверка замороженных гипотез, обучение LightGBM |
| Эмбарго | 2019 | разрыв не меньше горизонта метки (12 мес.) |
| Валидация-2 | 2020–2021 | выбор моделей и гиперпараметров |
| Бывший тест | 2022–2024 | **считается использованным**; только отчётность, решения по нему не принимаются |
| Чистый отложенный | 2025 – 06.2026 | открывается один раз, протокол открытия записывается в журнал |
| «Вперёд» | с даты заморозки правил | бумажные портфели |

Если подтверждённая гипотеза становится признаком LightGBM, модель переобучается так, чтобы период проверки гипотезы не попадал в обучение. Иначе признак помечается как «с утечкой» и в отчётные метрики не идёт.

**МЕТ-2. Журнал открытий отложенных периодов.** Каждое обращение к закрытому периоду записывается: дата, кто запустил, какая формула, результат. Код без записи в журнал к этим годам не обращается (проверка в функции загрузки данных).

**МЕТ-3. Значимость.**
- IC и спреды сопровождаются доверительным интервалом: блочный бутстрэп по полугодиям, ≥ 1000 повторов.
- Прирост «полная модель − B0» проверяется парным бутстрэпом по тем же блокам. В выводах указывается, значим ли прирост.
- В отчёте указывается число всех попыток (гипотезы + варианты LightGBM + отборы признаков) и q-значения FDR (Бенджамини–Хохберг) по всему журналу, а не только по гипотезам.

**МЕТ-4. Модель издержек HK** `config/costs_hk.yaml`:
- комиссия брокера, гербовый сбор по датам (0,1% до 08.2021, 0,13% до 11.2023, затем 0,1%), сборы SFC и биржи;
- половина спреда по оценке Corwin–Schultz или Abdi–Ranaldo; при отсутствии цен — по классу ликвидности;
- вход в ближайшую торговую сессию после `available_from`, учёт приостановок торгов;
- для коротких позиций: только бумаги из списка designated securities на дату и стоимость заимствования.
- Каждая гипотеза отчитывается в двух вариантах: **только лонг против подотрасли** и лонг-шорт.

**МЕТ-5. Работа «вперёд» начинается немедленно.**
- Пять подтверждённых гипотез (№ 2, 9, 23, 36, 39) и правила «победителей» (D1–D4, I1–I3, сырьё) замораживаются: формула, параметры и хеш кода.
- Ежемесячно и после каждого сезона отчётности формируются бумажные портфели (децили или топ-N внутри подотрасли) с фиксацией состава до выхода доходностей.
- Журнал портфелей пишется только дописыванием; хеш каждой записи хранится в git.
- Ежеквартальный отчёт: доходность к подотрасли, просадка, оборот.

**Приёмка:** реестр периодов используется всеми скриптами (проверка поиском по коду: нет жёстко прописанных годов). Первый бумажный портфель сформирован и закоммичен до 15.11.2026.

### 3.3 Данные и метки (П5–П8, П13)

**ДАН-1. Новая метка бедствия.** Событие наступает при любом условии:
- дефолт по облигациям или объявление о реструктуризации долга (источник: HKEXnews, ключевые слова и ручная проверка);
- приостановка торгов > 6 месяцев;
- падение цены > 70% за 12 месяцев с ростом долговой нагрузки;
- делистинг, ликвидация, going concern.

Отдельно хранится тип события и дата. Заранее составляется контрольный список известных дефолтов девелоперов HK 2021–2023 (≥ 30 компаний). Метка должна поймать ≥ 95% из них. После этого AUC и правила «долгового фильтра» пересчитываются.

**ДАН-2. Неизвестная цена выхода.** Вместо 0 хранится `exit_price_status ∈ {известна, оценка, неизвестна}`. Все метрики считаются в трёх вариантах: исключить неизвестные, считать −100%, считать 0. В отчёте показывается разброс. Правило пользователя «0 с флагом» остаётся вариантом по умолчанию.

**ДАН-3. Версии макро-рядов.** Для FRED используются версии ALFRED (`realtime_start`). Для рядов без версий задаётся лаг публикации по каждому ряду (`config/macro_lags.yaml`) и `available_from = конец периода + лаг`. Проверка: LightGBM с макро до и после исправления; разница записывается в каталог.

**ДАН-4. Пересчёты отчётности.** В `fact_fin` хранится каждая версия значения с датой документа, в котором она впервые появилась. Функции «на дату» берут последнюю версию, известную на дату. Для US XBRL используется поле `filed`, а не последнее значение companyfacts.

**ДАН-5. Валюты и единицы.** В `fact_fin` и `fact_kpi` хранятся исходная валюта, единица (тыс./млн) и курс на дату отчёта. Признаки считаются в одной валюте или как безразмерные отношения. Тест: доля отчётов HK в RMB/USD/HKD и выборочная сверка 50 отчётов вручную. **[сверить]**

**ДАН-6. Банки и страховщики.** Отдельный набор полей:
- банки: TBVPS, CET1, NPL, покрытие резервами, NIM, LDR;
- страховщики: EV, NBV, combined ratio, solvency ratio.

Золотой набор не меньше чем по 20 отчётам каждого типа; порог точности такой же, как для финансов (≥ 97%).

**ДАН-7. NAV-доходность.** Реализуется вторая целевая для типов бизнеса, где метрика стоимости доступна. Приоритет: банки (TBVPS), арендодатели (BVPS как приближение RNAV), добыча — позже. Покрытие и источник метрики хранятся колонкой.

**ДАН-8. Реестр источников** `docs/SOURCES.md`: источник, URL, условия использования, разрешена ли автоматизация, ограничения частоты, дата проверки условий. Новый сборщик не запускается без записи в реестре.

### 3.4 Качество извлечения и поиска (П9)

**КАЧ-1. KPI, уровень A.** Ручная выборка стратифицируется по отраслям и типам KPI. Для подтверждения точности ≥ 97% с нижней границей 95%-го интервала не ниже 95% нужно около 300 строк на каждую группу, которая выходит на уровень A. Ошибки судьи GLM считаются отдельно: доля, где судья и человек расходятся.

**КАЧ-2. Набор для поиска.** ≥ 200 вопросов с вручную отмеченными релевантными фрагментами (можно размечать полуавтоматически: кандидаты от модели, решение человека). Метрики: recall@10, nDCG@10, MRR. Судья-модель остаётся вспомогательной метрикой, её согласие с человеком измеряется.

**КАЧ-3. Ловушка для поиска.** Фрагмент из документа с будущей датой не должен попадать в выдачу `search_text(as_of=…)`.

### 3.5 Агент (шаги 11–12, П14)

**АГТ-1. Инструменты.** Каждый инструмент принимает обязательный `as_of` (по умолчанию — сегодня), возвращает JSON и список источников (`doc_id`, страница, таблица или SQL).

| Инструмент | Вход | Выход |
|---|---|---|
| `schema` | имя таблицы или пусто | описание таблиц и полей из `DB_SCHEMA.md` |
| `sql` | запрос только на чтение | ≤ 500 строк + текст запроса; таймаут 30 с; запрет DDL/DML |
| `search_text` | запрос, фильтры (компания, отрасль, годы) | фрагменты со ссылкой на документ и страницу |
| `get_doc` | `doc_id`, страницы | текст страниц |
| `peers` | компания | подотрасль и пиры на дату |
| `screen` | имя правила из каталога или формула | список бумаг с признаками |
| `backtest` | формула, период | IC, спред, интервалы; закрытые периоды недоступны (МЕТ-2) |
| `catalog` | фильтр | связи со статусом и эффектом |
| `propose_hypothesis` | формула, механизм, ожидаемый знак | запись в журнал до проверки; запуск проверки только после отметки пользователя |

**АГТ-2. Проверка чисел.** Пост-обработчик извлекает все числа из ответа и сопоставляет их с выводом инструментов этого диалога (с учётом округления и единиц). Число без источника помечается, ответ с такими числами не показывается как окончательный.

**АГТ-3. Набор вопросов (шаг 12).** ~150 вопросов, заморожен в git:
- типы: точечный факт, сравнение с пирами, скрининг, динамика KPI, вопрос о закономерности, вопрос с ловушкой (ответа нет, будущая дата, несуществующая компания);
- у каждого вопроса есть эталонный SQL или эталонный набор документов; ответ проверяется скриптом там, где это возможно;
- метрики: точность, доля чисел без источника (цель 0), доля корректных отказов на ловушках, число вызовов инструментов, время.

**АГТ-4. Тест узнавания.** Тесты L1–L6 из описания оформляются как часть набора: модель не должна давать правильные исходы по компаниям без вызова инструментов.

**Приёмка:** базовая модель 4–9B на наборе даёт отчёт по всем метрикам; доля чисел без источника после АГТ-2 равна 0.

### 3.6 Дообучение (шаги 13–14)

Требования описания сохраняются. Дополнения:
- траектории учителя проходят автоматическую проверку выполнением и АГТ-2; в обучение идут только успешные;
- вопросы из набора АГТ-3 и их близкие перефразировки исключаются из обучения (проверка по n-граммам и эмбеддингам);
- сравнение «база / база + примеры / база + LoRA» проводится на одном наборе с бутстрэп-интервалами; решение принимается по правилу из раздела 10 описания.

### 3.7 Рабочее место и цикл обновления (шаг 15)

**РМ-1. Цикл обновления** `pipeline/hk_update.sh` (затем `<рынок>_update.sh`):
1. загрузка новых документов (идемпотентно, по манифесту);
2. текст → разделы → факты → проверки качества;
3. добавление в базу с `available_from`;
4. пересчёт признаков только для затронутых компаний;
5. скрининг по замороженным правилам и запись в журнал портфелей (МЕТ-5);
6. отчёт об обновлении: сколько документов, сколько ошибок, какие бумаги вошли и вышли.

Повторный запуск без новых данных ничего не меняет. Падение на любом шаге не портит базу (запись во временную таблицу и атомарная замена).

**РМ-2. Экран идей и карточка.** Минимальный интерфейс: локальная HTML-страница или Streamlit, без внешних сервисов.
- Экран: фильтр по подотрасли, сработавшие правила, красные флаги, риск бедствия.
- Карточка: показатели на дату, ранги к пирам, KPI и их динамика, связи из каталога, цитаты со ссылкой на страницу, риски. Каждое число кликабельно и ведёт к источнику.

**РМ-3. Журнал решений.** Решение пользователя (взять, отклонить, наблюдать) с причиной и датой; используется для оценки работы «вперёд» и как обучающие данные для записок.

### 3.8 Перенос на другие рынки (шаг 16)

- До переноса `РУКОВОДСТВО_рынок_по_шагам.md` превращается в параметризованный конвейер: рыночные особенности описаны в `config/markets/<рынок>.yaml` (источники, валюта, календарь торгов, стандарты отчётности, издержки, правила коротких продаж).
- Первый рынок — US, финансы из XBRL с учётом ДАН-4. Критерий готовности рынка — те же проверки и тест-ловушка, что для HK.
- Для межрыночных связей (lead-lag) учитываются часовые пояса и календари торгов: признак рынка A используется на рынке B только после закрытия торгов A.

1. Проект воспроизводится из чистого клона и манифеста (ИНФ-1, ИНФ-2, ИНФ-5).
